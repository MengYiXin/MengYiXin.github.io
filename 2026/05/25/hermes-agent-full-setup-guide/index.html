Hermes Agent 满配指南：把 AI 助手调教成真正的工作系统
Yixin Lv5
 2026-05-25 17:04:00  
  • AI助手 
 
  • Hermes 
  • | AI工具 
  • | 个人效率 
  • | 工作流 
 

大多数人的 AI 助手使用方式是这样的：打开聊天窗口，问一个问题，得到答案，关闭窗口，下次再打开又是全新的对话。

这不是在用 AI，这是在”租用” AI。每一次对话都是孤立的，AI 不记得你是谁，不记得你上次做了什么，不了解你的偏好和项目背景。结果就是：你永远在从头开始，AI 永远像个刚入职的陌生人。

AI 助手的终极形态不是聊天窗口，而是一个可持续运转的工作系统。

本文是我自己折腾 Hermes Agent（一个开源 AI 助手框架）半年后的完整复盘，核心观点来自钱 sir 的 AIGC 文章，结合我自己落地过程中的实操经验。我会把每个层面拆得足够细，包括：怎么写 SOUL.md、记忆怎么存才对、Skill 什么时候建、以及怎么判断自己的 AI 助手到底是不是”满配”。

一、身份层：先定义它是谁的助手

SOUL.md 是整个系统的根基，它不是用来写”你是一个专业、友善的 AI 助手”这种废话的。

SOUL.md 是岗位说明书。你是在给这个 AI 角色写 job description，它上岗第一天就要知道：遇到什么情况该怎么做。

至少要写清楚这八件事：

它怎么称呼你？有些人喜欢被叫名字，有些人不喜欢被叫。你要让 AI 直接叫名字还是用敬语？写清楚。

它默认直接还是谨慎？有些人要的是快速响应的助理，有些人要的是会先质疑你的顾问。两种风格没有高下，但必须选一个。

遇到不确定的信息能不能猜？还是必须查证才能说？有些场景需要 AI 大胆推测（brainstorming），有些场景要求 AI 绝对准确（写合同/代码）。这里定义清楚，AI 才不会在不该大胆的时候乱猜，在不该保守的时候一直说”我不确定”。

什么时候必须查证，什么时候必须先问你？比如：调用外部 API 之前、对外发消息之前、改文件之前，这些都需要二次确认。边界画清楚，误操作的风险才可控。

能不能主动改文件？能的话，改之前要不要通知你？有些人要的是”我做，你来review”，有些人要的是”你来做主，我什么都不动”。前者效率高，后者风险低，根据自己的场景选。

做完任务要不要自动验证？比如发完邮件要不要检查已发送文件夹、部署完网站要不要跑一下 health check，这里定义清楚，AI 才不会把”执行完”当成”完成了”。

失败几次之后必须停下来？比如调用某个 API 重试 3 次还是失败，AI 应该停手报给你，而不是一直重试把系统打挂。这个阈值要设定。

一句话总结：SOUL.md 决定了这个 AI 以什么姿态介入你的工作。 写清楚，你面对的是一个有个性边界的助手；写模糊，你面对的就是一个时而过度热情时而过度保守的随机函数。

二、记忆层：不是越多越好，而是越准越好

我见过很多人往记忆里塞各种内容：今天的对话摘要、项目进度、临时 TODO，结果记忆越来越长，但 AI 每次还是在问”你这个项目是什么背景”。

根本原因是：记忆不等于信息积累，记忆等于可检索的、结构化的长期知识。

应该写进长期记忆的，只有六类信息：

用户的稳定偏好。比如”yixin 喜欢飞书通知，不喜欢邮件”、”输出格式要简洁，不要废话”、”遇到技术问题先排查网络”。这类信息一旦确定就不会变，写进去 AI 永远不用再问。

当前机器和项目环境。比如”家里电脑 IP 是 192.168.1.3”、”博客源文件在 WSL 的哪个路径”、”这个项目用的是哪个 API 接口”。这类上下文决定 AI 能不能直接执行命令，而不是问一堆环境问题。

已经做过的重要决策。比如”会理水库项目选了 AT800 3000 而不是 AT9508 G3，因为后者不支持 300V Pro”。这是决策审计，AI 以后遇到类似判断能追溯依据。

以后不能再踩的坑。比如”MiniMax API 调不通先查 base_url 是不是多了 /v1”、”Windows Git Bash 下 python3 是 Windows 原生二进制不是 Linux 解释器”。这类坑踩过一次就要记，第二次避免重复踩。

反复出现的工作流程。比如”博客发布流程是 git push source 分支，Actions 自动 build，不需要手动 hexo generate”。成熟流程固化进去，AI 以后可以独立执行。

外部系统的边界和禁区。比如”博客的 GitHub Actions 不能手动触发，只能等自动跑完”、”飞书群发消息需要二次确认”。这些是 AI 操作的护栏，避免它误闯禁区。

不该写进长期记忆的，也有三类：

一次性闲聊，不产生任何后续价值的对话内容。

原始聊天记录，过程数据和中间步骤（除非有决策价值）。

过期的任务状态，比如”正在处理中”这类临时状态应该清理掉，留着只会干扰判断。

记忆的核心原则是：宁可少，不要错。 一条准确的信息价值远高于十条模糊的摘要。

三、技能层：解决”会不会复用”，不是”记不记得”

Skill 和记忆解决的是两个不同的问题：记忆解决”记不记得”，Skill 解决”会不会用”。

记忆是静态的，告诉你”用户的默认语言是中文”。Skill 是动态的，告诉你”当用户说’帮我写一封英文邮件’时，具体操作步骤是：第一步打开邮件客户端，第二步拉取联系人列表，第三步……”。

Skill 是 AI 能力的真正的复利。你踩过一个坑，下次遇到同样的坑，如果没有 Skill，AI 还要再踩一遍；如果有 Skill，它可以直接调用固化好的流程跳过试错。

什么时候应该建立 Skill？

判断标准只有一条：这个流程以后还会不会遇到？ 如果答案是会，就写进 Skill。

具体场景包括但不限于：高频任务（每周都要做的日报生成、项目汇报）、踩过的坑（某个 API 的特定错误码意味着什么，应该怎么修）、复杂操作的多步骤流程（一次配置多台服务器）、外部系统对接（某个平台的标准操作流程）。

Skill 怎么写才是有效的？

一个有效的 Skill 不是”这个任务怎么做”的描述，而是一个可以直接执行的 checklist。它应该有触发条件（什么时候用这个 Skill）、操作步骤（一步一步怎么执行）、验证方法（做完之后怎么确认成功）、常见坑（哪里容易出错）。

以我自己为例：我的博客部署 Skill 写了 4000 多字，包含完整的 git push 流程、GitHub Actions 的状态检查、域名解析验证、以及中途踩过的 11 个坑。每次发布博客，AI 按照 Skill 执行，不需要我再操作一遍。

Skill 是活的文档，每次实战都是更新机会。 踩到一个 Skill 没覆盖到的坑，第一时间补进去，而不是记在脑子里。这才是 AI 越用越顺的真正原因。

四、模型层：满配不是全程最贵，而是分层使用

很多人有一个误区：最强模型应该处理所有任务。结果就是成本爆炸、响应变慢、上下文被无关内容填满。

真正的满配是分层使用，让每个模型各司其职。

主模型（通常是最强的，比如 Claude Sonnet）负责：复杂推理、关键决策、创意写作、需要深度理解的长文档。这类任务必须用最强模型，没有捷径。

压缩模型（通常是轻量模型）负责：会话总结、上下文压缩、简单问答。当上下文快用完时，压缩模型把有价值的信息提炼出来，交给主模型继续。

视觉模型（VL 模型）负责：图片理解、截图分析、图表解读。这类任务不需要强推理，但需要专门的多模态能力。

搜索模型负责：资料整理、历史召回、快速检索。当用户问到一个需要实时信息的问题，搜索模型先拉取相关内容，主模型再基于此推理。

轻量模型负责：标题生成、摘要、格式化输出。简单命名类任务不需要调用主模型 API。

分层使用的核心收益是：成本降下来，速度提上去，而关键任务的质量不受影响。 非关键任务交给轻量模型处理，主模型只处理真正需要它的时候。

实际配置时，通常在 config.yaml 里指定不同任务的模型路由规则。比如我自己的配置里，视觉任务走 MiniMax VL，搜索走 DDGS，代码任务走 Claude Code，常规对话走 MiniMax M2。

五、工具层：MCP 不是越多越好

MCP（Model Context Protocol）是 AI 接入外部能力的接口，但它不是越多越好。

接入的每一个工具，都是 AI 可能误操作的潜在入口。工具越多，边界越模糊，误操作的面越大。

接入工具的三个原则：

按需接入。不要因为”这个工具看起来很厉害”就接，而是因为”这个工具是这个工作流里明确需要的”才接。如果一个工具没有对应的工作流，不要为了”看起来完整”强行接。

边界清楚。每个工具能做什么、不能做什么，必须定义清楚。比如文件工具的访问范围是哪些目录？消息工具能不能主动推送还是只能被动回复？发布工具是直接发还是草稿模式？边界越清楚，误操作概率越低。

外部动作必须二次确认。凡是涉及对外的操作（发公众号、发飞书消息、删除文件、调用付费 API），AI 执行前必须经过用户确认。宁可多一步确认，不可事后追责。

一个简单的判断标准：如果你不确定某个工具该不该接，那就不接。 等到有具体的工作流需求再接，比提前接进去然后踩坑要好得多。

六、执行层：命令跑在哪里，决定了风险有多大

AI 执行命令的环境，不是一个可以忽略的细节。

local（本地）：命令直接跑在你自己的机器上。优点是可以访问本地文件、网络和所有资源。缺点是一旦出错，可能直接影响本机环境。我一般用 local 处理那些”我知道在做什么、有明确预期”的轻量任务。

docker（容器隔离）：命令跑在一个隔离的容器里，和宿主机环境完全分离。适合运行不确定的脚本、批量处理任务、第三方项目。容器一出问题，重启容器就恢复，不会影响本机。我处理任何爬虫类任务、第三方脚本、不确定安全性的代码，一律走 docker。

SSH/云端：命令跑在远程机器上。适合需要更强算力的场景、长期运行的后台任务、或者需要访问特定网络环境的任务。这类任务一般交给云端处理，本地只负责监控和结果回收。

核心原则是：明确每个 Agent 的执行边界在哪里。 它能操作本地文件吗？能访问哪些目录？能执行哪些命令？能连接哪些网络？边界画清楚，安全性才有保障。

七、迁移层：换系统不是搬家，是一次重新开始

如果你从 OpenClaw 或者其他 AI 助手框架迁移到 Hermes，不要把旧东西原样搬过来。

迁移的真正价值不是”把原来能用的功能迁移过去”，而是”借这个机会做一次彻底的清理”。

正确的迁移步骤是这样的：

第一步，先 dry-run，看新系统会迁移哪些内容。很多框架支持只读模式跑一遍，模拟迁移但不实际执行。先看清楚。

第二步，用户偏好、稳定记忆、成熟的 Skill 可以迁。这些是经过实战验证的，有价值的资产。

第三步，临时配置、废弃的 MCP、过期 token 要清理掉。这些是历史包袱，迁过去不仅没用，还会在以后制造隐患。

第四步，密钥单独检查。认证信息不要依赖自动迁移工具，手动验证一遍，确保每个系统的接入都是正常的。

第五步，迁移后跑完整的健康检查。消息通道通不通？工具能正常调用吗？权限设置对不对？逐个验证，不要假设。

迁移不是搬家，是一次重新设计的机会。 趁换系统，把以前不规范的地方一并修正，比在新系统里继续沿用旧习惯要高效得多。

写在最后

回到开头的问题：你的 AI 助手，是真的在帮你工作，还是只是一个随时可以重启的聊天窗口？

如果你每次打开对话都需要重新解释背景、每次都要叮嘱它不要做某些事、每次它完成任务你都要亲自检查——那它本质上还是一个工具，而不是一个工作系统。

真正的 AI 工作系统，是你把规则制定清楚之后，它可以独立运转的。你定义边界，它在边界内自主执行；你固化流程，它按流程不重复踩坑；你建立记忆，它记住值得记住的，放过不值得纠结的。

这不是”AI 越来越聪明”，这是你把经验固化的能力越来越强。

系统搭好之后，每一次使用，都是在给系统添砖加瓦，而不是每次从头开始。

本文基于钱 sir AIGC 的核心框架，结合 Hermes Agent 的实际配置经验整理。如果你也在搭建自己的 AI 工作系统，欢迎交流。
